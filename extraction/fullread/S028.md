## 2. Eligibility
Yes, with a narrow scope. Local LLMs (Mistral-7B on a Raspberry Pi 5 and llama3.2 3B on a PC) connect to the plant's control layer: they read the PLC (programmable logic controller) through MQTT/OPC UA and Modbus TCP, the SCADA system through OPC UA, and MES/ERP through a REST API. They answer operator questions in natural language, live in an operating precast concrete plant (Frumecar S.L.). The LLM only advises a human. The tested LLM never writes setpoints or actuator commands. A separate Telegram "Control Tank" bot does accept /on, /off and /sp:XX commands (p.6), but it is not described as LLM-mediated and no tests of it are reported. The process is real industrial production, not an adjacent domain. This is a core paper of the advisory / operator-assistant type, with E5 evidence.

## 3. What was built, in plain words
The plant is a real precast concrete factory. The paper names one process explicitly: level control of the mixing-water tank, which sets the water–cement ratio. The existing PLC/SCADA automation runs that process, and no LLM touches the loop. The work adds a "reference cognitive architecture" from the authors' earlier paper [10], running on a Raspberry Pi 5, to that automation. It has five layers: Spanish speech recognition and synthesis; a Mistral-7B-Instruct-v0.2 model (GGUF 4-bit, run with llama-cpp-python); a layer that extracts parameters and checks request validity; a data-access layer to the five automation-pyramid levels; and JSON traceability logging (p.4).

This paper adds an "event-driven stack" in Docker on an x86 PC without a GPU (p.6–7). Node-RED (a visual flow tool) polls the plant state over Modbus TCP and an /estado-planta REST endpoint. It flags six kinds of event: a process-variable deviation of more than ±5%, a mode change, a setpoint change, an alarm, an alarm recovery, and a communication failure. n8n (a workflow orchestrator) runs on 20 s cycles. It logs readings to PostgreSQL and decides whether to update the context incrementally or regenerate it in full every 30 min. Ollama runs llama3.2 3B, which summarises the history and current state into an "Industry Report" of at most 8 lines. Its prompt contains anti-hallucination rules: no speculation about missing data, and separate alarm counters (p.6). When an operator asks a voice question, Mistral-7B answers from this pre-built report instead of querying the protocols live. The LLM output is spoken text to a human. There is no validator or gate on LLM output beyond these prompt rules and Layer 3's request-validity check. Actuation is unaffected by the LLM. The Telegram bot's on/off and setpoint commands are on/off and discrete, and they are not LLM-driven.

## 4. Each tested setup
There is one architecture: an LLM operator-query assistant with event-driven pre-built context, in the live plant. All experiments used an ambient temperature of 24 ± 1 °C (p.7).
- **Response time (Exp. 1):** 15 queries (5 simple, 5 moderate, 5 complex), each run 3 times (p.7). The comparator is the authors' earlier reactive LLM architecture [10], so this is LLM versus LLM, and the reactive numbers come from that paper. Metrics are the mean, SD, median, IQR and Cohen's d. The factor varied is query complexity.
- **Thermal (Exp. 2):** CPU temperature of the Raspberry Pi logged every 10 s over a 30 min session, compared with the reactive paradigm [10].
- **Modbus latency (Exp. 3):** 10,163 reads on the mixing-water tank process, with no LLM involved.
- **Reliability (Exp. 4):** 30 min of autonomous operation with 41 random queries, measuring success rate, failure rate and availability. "Success" means a valid response with no timeout or exception (p.7). Answer correctness is not checked.
- **Case study:** one production-feasibility query (45 m3 of C25/30 concrete), comparing traditional manual navigation, the reactive LLM system and the event-driven LLM system. The manual figures are carried over from [10]. There is a single representative execution (p.11).

No disturbance, fault or adversarial query was tested. No tuned non-LLM controller or rule-based report generator was compared.

## 5. Results
- Response time (lower is better; n = 15 per level): "mean response time of 9.84 s (SD = 4.12 s), compared with 14.19 s under the reactive paradigm" (p.8). For moderate queries it was 11.23 s against 16.45 s (31.7%). For complex queries it was "16.47 s (SD = 4.23 s) compared with 23.24 s" (29.1%) (p.8). Cohen's d was 0.71, 0.99 and 1.22 (p.8).
- Thermal (Pi 5 CPU; lower is better): "Peak temperature 79.6 °C … 71.2 °C"; the throttling margin went from "5.4 °C" to "13.8 °C"; SD fell by 41.6% (Table 2, p.9).
- Communication: "Mean read time 9.14 ms" over 10,163 Modbus reads, which is under 0.1% of response time (p.10).
- Reliability: "completed all 41 queries, achieving a 100% success rate with no partial or critical failures" (p.10). The denominator is 41 queries over 30 min. The metric measures responsiveness, not answer accuracy.
- Case study (single run): total time was 16–24 min for manual navigation, 17.9 s for the reactive system and 13.2 s for the event-driven system, so the event-driven system was "73–109×" faster than traditional (Table 5, p.11–12). Mistral inference time was "5.8 s vs. 7.2 s" (Table 6, p.12).
- Model selection cited from other work: Mistral-7B reached 90% accuracy on Spanish industrial commands, against 60% for Llama-2-7B, 10% for Phi-2 and 30% for TinyLlama [26] (p.5). This was not measured in this paper.
- **LLM versus non-LLM:** the only non-LLM comparison is with manual HMI/system navigation, on information-access time, in one case study whose manual figures come from the earlier paper. The paper does not show the LLM beating a tuned controller or a rule-based or dashboard alternative on any control metric. Answer correctness is not measured.

## 7. Terms to define
- Event-driven architecture (EDA): the system reacts to detected process changes and does not compute only when a user asks.
- Reactive paradigm: the earlier design, which queries all automation levels and runs inference only when the operator asks.
- Industry Report: an LLM-generated summary of the plant state of at most 8 lines, pre-built by llama3.2 and used as context for the answering LLM.
- Delta/full update: an incremental context refresh triggered by an event, versus a full regeneration every 30 min.
- Automation pyramid levels 1–5: field/PLC, SCADA, MES, ERP and so on, reached through MQTT, OPC UA and REST.
- Node-RED / n8n: low-code tools for event detection and workflow orchestration.
- Ollama / GGUF Q4_0: a local LLM runtime and a 4-bit quantised model file format.
- Throttling safety margin: the gap between the peak CPU temperature and the 80 °C point where the Pi 5 starts throttling.
- Partial failure: a query that hit a timeout or exception and recovered within 30 s without a restart.
- Cohen's d: the standardised mean difference between the two paradigms.
