## 3. What was built, in plain words
The plant is real hardware: a small acrylic greenhouse (50 x 50 x 60 cm) with a live plant inside. It has a 100 W ceramic heater, intake and exhaust fans (68 m3/h), LEDs, irrigation and a sensor array (p.1-2). The task is to regulate air temperature to a time-varying reference using two actuators. The heater duty cycle uh takes values from 0 to 1 in steps of 0.05, so it is quasi-continuous. The fan uf is on/off (p.2).

There is no conventional controller in the loop. The LLM is the controller: at each step it receives a natural-language prompt containing the target, current and ambient temperatures, and it returns uh, uf and a short rationale (p.3). The paper describes no validator, safety gate or human approval before the command reaches the actuators. Guardrails such as "do not act unless at least one row was retrieved" are proposed only for the future (p.7).

Three architectures, built in LangChain on OpenAI GPT-4o (p.3, Fig. 2):
- **Prompt-only:** a single LLM call with no tools.
- **SQL-assisted:** the agent lists tables, writes SQL queries against a database of past experiments (for example, earlier MPC runs on the same rig), and picks controls by imitating similar past cases.
- **Prediction-assisted:** the agent proposes candidate constant control sequences and simulates them with a predictor. The predictor is a linear ARX model, an LSTM, or HAM (CoSTA: a physics-based heat balance plus a neural-network residual correction). The agent then chooses the candidate whose predicted temperature is closest to the target.

Prompting is zero-shot. LLM temperature is 0 ("Te0"). A "-P" variant adds a sentence telling the agent that minimal fan use is the first priority (p.3). There is no fine-tuning.

## 4. Each tested setup
All runs use the same physical greenhouse and the same varying reference temperature ("Reference 2"). Judging from the figure axes, each run lasts about 6 hours, with time in minutes (Fig. 4-5, p.4-5). The training data were sampled every 60 s (p.3). The control update interval for the LLM runs is not stated. LLM latency is not reported. Each controller appears to have been run once; no repeats or variance are reported. No non-LLM controller is run as a baseline in this paper. MPC and RL comparisons are deferred to Rasheed et al. (2025) (p.5). Metrics are the MAE of temperature tracking and the mean heater and fan usage (fraction of time or duty cycle) (Fig. 6, p.5). What was varied across runs: the tool (none, SQL, Linear, LSTM, HAM) and the presence of the actuation-penalty prompt.

- **Setup A, prompt-only LLM (LLM-Te0, LLM-Te0-P):** GPT-4o with no tools; two runs (with and without the penalty).
- **Setup B, SQL-assisted LLM (LLM-SQL-Te0, LLM-SQL-Te0-P):** the agent queries a historical database of the rig's experiments, including MPC runs.
- **Setup C, prediction-assisted LLM (LLM-Linear/LSTM/HAM-Te0, with and without -P):** the agent scores candidate actions with a learned or hybrid predictor; six runs. A separate offline comparison of the predictors shows HAM and LSTM with lower MAE than Linear and the pure physics-based model (Fig. 3, p.4).

## 5. Results
- **Tracking MAE (Fig. 6a, p.5; lower is better; read from the bar labels in the page image, so the last digit is uncertain).** Values in deg C: LLM-SQL-Te0 0.207, LLM-LSTM-Te0 0.228, LLM-SQL-Te0-P 0.264, LLM-Te0-P 0.285, LLM-Te0 0.321, LLM-Linear-Te0 about 0.37, LLM-Linear-Te0-P about 0.38, LLM-HAM-Te0-P about 0.46, LLM-HAM-Te0 0.575, LLM-LSTM-Te0-P 0.640. Each value comes from one run. The text agrees: "the best values are achieved by the SQL-assisted and LSTM-assisted variants without penalty" (p.5).
- **Viability without tools (p.4):** "Overall, Fig. 4 shows that a pure LLM controller is already viable." This is qualitative. Prediction-assisted variants "still oscillate once they are close to the target" (p.4).
- **Penalty effect (p.5):** "all '-P' controllers reduce fan time as intended." This is measured as mean fan usage (fraction of time; lower means less actuation), shown in Fig. 6b with values roughly 0.1 to 0.8. The prediction-assisted variants pay for this with tracking error: "they also show a larger tracking error" (p.5). For example, LLM-LSTM MAE rises from 0.228 to 0.640.
- **Trade-off (p.5):** "There is no single controller that is best on both MAE and actuator economy."
- **Failure anecdote (Example B, p.6):** the SQL agent stopped before its second query and "hallucinated by providing an arbitrary control input": heater 0.75 and fan ON, without retrieved evidence. This is one anecdote; no failure rate is reported.
- **Tool-use examples (p.6-7):** with the LSTM, the agent evaluated four candidates (predicted end temperatures 26.80, 30.08, 28.43 and 28.93 deg C) and chose heater 0.8, avoiding overshoot. With HAM it chose heater 1.0.
- **LLM versus non-LLM:** the paper does **not** show the LLM beating any non-LLM alternative. No PID, MPC or rule-based controller is run alongside it. MPC data are used only as a retrieval source for the SQL variant.

## 7. Terms to define
- HAM (Hybrid Analysis and Modeling): a physics model combined with a data-driven correction.
- CoSTA (Corrective Source Term Approach): a neural network learns a residual source term added to the physics-based heat-balance ODE.
- PBM: physics-based model (here, the heat balance without the correction term).
- ARX: linear autoregressive model with exogenous inputs (past temperatures plus heater and fan inputs).
- LSTM: long short-term memory recurrent neural network, used as a one-step temperature predictor.
- LangChain: Python framework for building LLM agents that call tools such as SQL databases and models.
- Te0 / Te1: LLM sampling temperature (0 is deterministic).
- -P: prompt variant that makes minimal fan usage the first priority.
- Duty cycle: fraction of time the heater is on; the setpoint for heater power.
- MAE: mean absolute error between measured and reference temperature (deg C).
