## 3. Background use
- **Architecture.** The LLM sits at the supervisory reconfiguration level of the standard active fault-tolerant control loop. It takes the fault context from fault detection and diagnosis, retrieves plant context from a knowledge graph, and proposes an action. An external validator (a symbolic check or a digital-twin rollout) judges the action before anything is actuated. If the validator rejects it, the LLM is reprompted with the reason until a budget runs out, and then an engineered safety fallback takes over. The regulatory PID loops are not touched (pp.2-3, Fig. 1, Eqs. 1-3).
- **Design principles.** There are three recovery patterns: (A) discrete routing with a symbolic validator, (B) bounded setpoint adaptation with a simulation validator, and (C) staged hybrid recovery. The paper names when an LLM is the wrong tool: when a rule base already covers the problem, when millisecond reaction is needed, or when the fault space is narrow (pp.3-4, Table 1). Structured rejection feedback converges faster than a generic rejection, and reprompts should be capped by repeated failure category (p.4). The deployment checklist covers cloud versus on-premise latency, the knowledge graph as the main cost, no execution authority for the LLM, logged decision traces, the IT/OT boundary and prompt injection, a pinned model identifier, and regression suites gated on the validator verdict (pp.4-5).
- **Testbeds.** There are two open environments: a mixing module run as a finite state machine (pump, line and leak faults that force a bypass route) and a CSTR under three PID loops (fouling, pump degradation and cooling-valve faults), with plug-in interfaces for recovery and validation methods (pp.5-6).
