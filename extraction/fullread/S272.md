## 2. Eligibility
Yes. An LLM agent (IBM Granite-4.1 8B) connects to an MPC controller through tools. It attaches or detaches objective-function primitives and sets their arguments (reference speed, preferred steering direction) while the loop runs. This is tested in simulation. The domain is adjacent: autonomous driving in the CARLA simulator (vehicle). Recommended tier: core, as an adjacent-domain paper.

## 3. What was built, in plain words
The plant is a simulated vehicle (the "vehicle.nissan.patrol" model) in CARLA, an open-source driving simulator (p.4). There is no hardware. The controller that moves the actuators is an MPC solved by "Fourier MPPI", the authors' extension of Model Predictive Path Integral control. MPPI is a sampling-based MPC: it draws S = 256 random input sequences, weights them by exp(−cost/T), and averages them. Fourier MPPI samples the coefficients of a truncated Fourier series (L = 4) instead of the raw input sequence (p.3–4). The model inside the MPC is a kinematic bicycle model plus a linear speed model, identified from data, with a sampling interval of Δt = 0.04 s (p.4). The inputs are continuous: steering, throttle in [0,1], and brake in [0,1]. All constraints are soft penalties in the cost (p.3).

The MPC cost is the sum of a mandatory term and "primitives" (small objective terms) taken from a pool. The pool has three: J1 path tracking at reference speed v_ref, J2 obstacle-avoidance penalty, and J3 soft preferred-steering-direction bias (p.4–5).

The LLM agent runs asynchronously from the MPC loop and is triggered by user messages (p.5). Its system prompt lists the currently attached primitives and the available tools. It calls tools through the Model Context Protocol (MCP), a standard for listing and invoking tools. The tools are run_center_lane(v_ref), run_left_lane(v_ref) and set_preferred_steering_direction(p) (p.5). The agent's output is a tool call that rewrites the MPC objective. There is no validator, human approval or simulation check on that output. The only safeguards are design choices: a restricted tool set ("the accessible tools are constrained for safety", p.2) and a mandatory objective term that cannot be detached (p.3). The paper describes no fine-tuning; the model is used through prompting and tools.

## 4. Each tested setup
**Setup A: Scenario 1, steering preference (p.5).** A circular obstacle sits on the reference path, and J1 (center lane, v_ref = 15 m/s) plus J2 are attached.
- Baseline: ten trials with no user message.
- LLM cases: User Message 1, "Let's try to avoid obstacles from the right, shall we?", and User Message 2, the same request for the left. The LLM must call set_preferred_steering_direction with the correct direction.
- Number of runs: the number of trials in the message cases is not stated. Fig. 3b shows several trajectories per case.
- Comparator: the same MPC without a message. This is not a competing non-LLM method for the semantic task.
- Metrics: which side of the obstacle the vehicle passes, and trajectory plots.

**Setup B: Scenario 2, emergency response (p.5–6).** J1 is attached (center lane, 15 m/s). Two messages arrive in sequence: "An ambulance is coming behind us. We'd better let them pass." and then "Thank you. The ambulance is gone."
- Outcome measured: the tool calls the LLM makes, and the trajectory (Fig. 4).
- Number of runs: one run is shown.
- Comparator: none.
- Metrics: none quantitative.

Nothing else is varied. There is no comparison of LLMs, prompts or temperatures, and no latency measurement.

## 5. Results
- **Scenario 1 baseline (p.5):** "The vehicle passes the right side of the obstacle 3 times and the left side 7 times." Out of 10 trials without a message, the pass side varies because Fourier MPPI is stochastic.
- **Scenario 1 with a message (p.5):** "In the User Message 1 case, the vehicle passes on the right in all trials. In the User Message 2 case, the vehicle passes on the left in all trials." The number of trials (the denominator) is not stated. The LLM called set_preferred_steering_direction with "right" and "left" respectively (p.5).
- **Scenario 2 (p.6):** "the agent invokes the tool 'run left lane' with the reference speed vref = 0". After the second message, it called run_center_lane with v_ref = 15 m/s, which restored the original specification (p.6). The authors credit this recovery to the system prompt, which lists the initial primitives (p.6).
- **LLM against a non-LLM method:** the paper does not show the LLM beating a non-LLM alternative. The only contrast is MPC with and without the language-derived primitive. No control metrics are reported (no tracking error, cost or timing). There is no count of LLM tool-call correctness across repeated LLM queries, and no off-nominal or adversarial messages are tested.

## 7. Terms to define
- MPC (model predictive control): a controller that, at each step, optimizes inputs over a prediction horizon using a model of the plant.
- MPPI (Model Predictive Path Integral): a sampling-based MPC. It samples input sequences and averages them, weighting each by its cost.
- Fourier MPPI: the authors' MPPI variant. It samples Fourier-series coefficients of the input sequence to cut the sampling dimension.
- Primitive: a reusable unit of an objective, constraint or model that can be attached to or detached from the MPC.
- Pool: the predefined set of available primitives.
- Agent step τ: the agent's discrete event index, independent of the control step t. It advances when a new message or tool result arrives.
- MCP (Model Context Protocol): Anthropic's standard syntax for listing and calling tools.
- CARLA: an open-source autonomous-driving simulator.
- Kinematic bicycle model (KBM): a simple vehicle model of position and heading driven by steering angle and speed.
- Soft constraint: a constraint enforced only as a penalty in the cost, not as a hard limit.
