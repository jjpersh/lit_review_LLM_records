## 2. Eligibility
Yes. LLM agents (GPT-4o-mini, GPT-4.1-mini) produce corrective control actions. In one case these are on/off actuator commands; in the other they are setpoints for PID loops. The actions are applied to a simulated plant after deterministic simulation-based validation. The plants are process systems: a simulated Festo mixing module (multi-tank batch sequence, based on a lab rig) and a simulated CSTR under three PID loops. Not adjacent. Core.

## 3. What was built, in plain words
This is an active fault-tolerant control (FTC) framework that runs after a fault is detected. Both plants are Python simulations; no hardware is in the loop. The Monitoring Agent is deterministic or data-driven, not an LLM. It flags faults using statistical thresholds (for the CSTR: mean, standard deviation and three-sigma limits from fault-free runs, p.9). Fault localization is assumed and lies out of scope (p.9).

Two LLM agents follow:
- **Planning Agent.** It retrieves a state-machine subgraph (states, transitions, guards) from a knowledge graph using SPARQL queries. This is "Graph RAG" over the CPSMod ontology, stored in GraphDB. The agent picks a minimal-risk recovery path or target state.
- **Action Agent.** It retrieves the actuator and limit subgraph and outputs commands as short JSON.

The commands differ by plant:
- **Mixing module:** the set of on/off valves and pumps to activate. Actuation is on/off.
- **CSTR:** new setpoints (T_sp, L_sp, F_in,sp) for three standard PID loops (inlet valve V1, outlet pump P2, cooling valve V3). Here the PIDs move the actuators continuously.

Before anything reaches the plant, a Simulation Agent rolls the proposal out on the digital twin (the "DPPT"). A deterministic Validation Agent then checks the result against interlocks, envelopes, recovery time, loop-performance bounds and actuator-rate limits, and returns Approve or Revise. On Revise, a Reprompting Agent feeds the violations back to the LLM, either from templates or as LLM-generated text. After the reprompt limit (5 in the CSTR), control passes to a deterministic safety fallback (pp.7–8, p.11). There is no human approval step. Both models are prompted, not fine-tuned.

## 4. Each tested setup
**Setup A: Mixing module (simulated Festo lab rig), discrete on/off recovery.**
- Five injected faults: pump_failure, pump_degradation, clogging, sensor_fault, leakage.
- Runs: n = 10 per fault per model, for 2 models, giving 60 runs per model (Table 1, p.10). In addition, 10 fault-free baseline trials per model "confirming" nominal steering; no numbers are given for these (p.9).
- Comparator: none. There is no non-LLM recovery baseline (for example a graph shortest-path search or a rule table), even though the authors mention that discrete shortest-path selection is possible (p.6).
- Metrics: success rate, recovery rate after reprompting, plan correctness, action correctness, action precision and recall against a ground-truth actuator set, decision latency, wall-clock time, tokens.
- Varied: fault type and LLM.

**Setup B: CSTR (simulated) under three PID loops, continuous setpoint adaptation.**
- Three injected faults: fouling, pump_degrade, cool_stuck_closed.
- Runs: n = 10 per fault per model, giving 30 runs per model (Table 2, p.11). The LLM decision loop is typically triggered once per run.
- Comparator: none. The deterministic fallback exists, but its runs are counted as failures and it is not compared as a baseline.
- Metrics: success (validated LLM setpoint applied within 5 reprompts), recovery rate, wall-clock time, Action Agent latency, tokens. Figure 7 shows temperature and actuator trajectories, but no IAE, overshoot or settling-time numbers are reported.
- Varied: fault type and LLM.

## 5. Results
**Mixing module (Setup A)**
- "GPT-4.1-mini achieved perfect performance with a 100% success rate across all 60 runs, requiring no corrective reprompts" (p.10).
- "GPT-4o-mini succeeded in 51 of 60 runs (85%)" (p.10). The failures were in pump_degradation (5/10) and sensor_fault (6/10) (Table 1).
- Recovery rate is the share of runs that needed reprompting and were then corrected; higher is better. "only 44% of runs requiring correction in pump_degradation and 33% in sensor_fault could be recovered" (p.10). The overall value for GPT-4o-mini is 80% (Table 1).
- Action precision is correct activations over all activations; higher is better. "action precision of only 61.4% (71 false positive activations out of 184 total)" (p.10), for GPT-4o-mini in pump_degradation. Also: "only 52% of iterations achieved a fully correct actuator configuration" (p.10).
- Plan correctness: "plan correctness dropped to 64.6%" (p.10), for GPT-4o-mini in sensor_fault.
- Action recall: "All 780 expected activations for GPT-4.1-mini and all 895 ... for GPT-4o-mini were correctly issued" (p.10).
- Latency: "GPT-4.1-mini: 2.4 s planning, 2.2 s action; GPT-4o-mini: 2.4 s planning, 3.0 s action" (p.10).
- Wall-clock time: "Mean wall-clock time was 32.7 s for GPT-4.1-mini and 40.7 s for GPT-4o-mini" (p.10).
- Tokens: about 54–58k input tokens per run (Table 1).

**CSTR (Setup B)**
- "GPT-4.1-mini achieved a success rate of 28∕30 (93.3%) across all runs, while GPT-4o-mini achieved 23∕30 (76.7%)" (p.11).
- cool_stuck_closed: GPT-4.1-mini succeeded "in all runs (10∕10), typically requiring reprompting (mean ≈ 2 reprompts)". GPT-4o-mini "succeeded in only 4∕10 runs" (p.11), with 0% recovery (Table 2).
- Fouling: 8/10 for GPT-4.1-mini and 9/10 for GPT-4o-mini (Table 2).
- Action latency: "lower mean per-call action latency (2.1 s vs. 2.7 s)" (p.11). Wall-clock time per run was 51.9 s and 43.3 s (Table 2).
- In the fouling case, the validated intervention cut the inlet-flow setpoint, which kept the plant stable at reduced throughput (p.11, qualitative only).

**Comparison with non-LLM methods:** none. The paper does not show the LLM beating a non-LLM alternative on any measure. All comparisons are between the two LLMs.

**Inconsistency:** p.11 states that GPT-4.1-mini reached 100% plan and action correctness "apart from fouling", and p.12 states "GPT-4.1-mini achieved 100% success across all scenarios". Table 2, however, shows 8/10 for fouling.

**Authors' limitations**
- Building the knowledge graph takes effort (p.12).
- Unknown faults cannot be validated by the twin (p.12).
- The latencies "preclude application to processes with hard real-time constraints" (p.12).
- Scalability is untested, and the framework assumes a representative twin; model mismatch and noise were not studied (p.12).
- Cloud LLMs were used, which is for research only (p.12).

## 7. Terms to define
- Active FTC: online compensation of fault effects to keep operating safely.
- DPPT (Digital Process Plant Twin): the tool layer holding plant data, models and a simulation service used to pre-test actions.
- Graph RAG: retrieval of knowledge-graph subgraphs (here via SPARQL templates) appended to LLM prompts.
- CPSMod: the authors' modular alignment ontology joining standards-based design patterns for structure, function, behavior and faults.
- ODP (ontology design pattern): a reusable ontology module, here built on VDI 2206, VDI 3682, UML State Machine, OpenMath and DIN 17359.
- T-Box / A-Box: the ontology schema / the plant-specific instance data.
- SPARQL CONSTRUCT: a graph query that returns a self-contained subgraph.
- Success rate: the run ends in a validated LLM action, with no safety violation, within the reprompt limit (fallback runs count as failures).
- Recovery rate: the share of reprompted runs that end successfully.
- Action precision / recall: correct activations over all issued / required activations issued, against a ground-truth actuator set.
- Reprompt limit: the maximum number of validator-driven retries (5 in the CSTR) before the safety fallback takes over.
