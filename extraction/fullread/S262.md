## 2. Eligibility
Yes. A generative LLM (gemma3:12b, run locally) turns operator natural-language requests into JSON parameter updates for a GEKKO MPC: reference-trajectory time constants, move penalties, actuator limits and setpoint dead-bands. A human approves each update before it reaches the MPC, which runs on the physical TCLab two-heater thermal rig, a standard process-control teaching benchmark. The LLM also writes text summaries of controller performance. This is a tested setup on lab hardware, so the paper is core, and the domain is not adjacent (it is a process benchmark presented as a proxy for pharmaceutical unit operations).

## 3. What was built, in plain words
The plant is the TCLab (Temperature Control Lab). It is real hardware: an Arduino board with two heaters and two temperature sensors that are thermally coupled, used here as a two-input, two-output system (p.2). A GEKKO MPC moves the actuators. GEKKO is a Python optimization suite, and the MPC uses a first-principles heat-transfer model, an L1-norm objective with a setpoint dead-band, and a 5 s sampling time (p.2–3). It writes continuous heater power levels in percent. The LLM never writes heater commands. It sits in a supervisory tuning layer. An operator types a request (e.g. "avoid overshoot"). The LLM receives a system prompt of about 900–950 tokens describing its role, the adjustable MPC parameters, their effects and the JSON format to return (p.3). It also receives a natural-language log of recent process data that custom Python functions rebuild at each control step (temperatures, setpoints, heater values, overshoot). It replies with text plus JSON commands that change GEKKO attributes (CV.TAU, CV.SPHI/SPLO, MV.DCOST, MV.UPPER/LOWER and others; Table I, p.4). A Python function pulls the JSON out of the reply and asks the operator for "y"/"n" approval. Approved commands go over WebSocket to the MPC server, which applies them (p.3). Apart from GEKKO's own constraint handling, there is no automatic validator. Four models were tried (gpt-oss 20b, deepseek-r1 8b, llama3.2 3b, gemma3 12b). gemma3:12b was chosen for its 128k context and because it ran fast enough on a local 32 GB GPU (p.3). There is no fine-tuning and no tool use. A second feature, "automated analysis feedback", has the LLM summarize controller performance in text when the operator asks (p.3).

## 4. Each tested setup
**Setup 1: LLM proposes MPC tuning changes, operator approves, MPC runs on the TCLab hardware.**
- Conditions: a baseline run with default tuning, stepping both temperatures from ambient to 35 °C. Then four scenarios, each a new run from ambient to 35 °C, some followed by a step to 40 °C (p.3):
  - (1) aggressiveness: T1 faster, T2 slower;
  - (2) overshoot avoidance;
  - (3) smoothing Heater 2;
  - (4) input and output limits (T1 within 38–42 °C, Q1 within 20–70%).
- Number of runs: one run per scenario. No repeats or variance are reported.
- Comparator: the same MPC with default tuning ("moderate-performance controller with no special optimization", p.3). There is no comparison with a human engineer's tuning, an optimizer-based auto-tuner or another non-LLM translation method.
- Metrics: overshoot (°C) and rise time (s) for some scenarios, otherwise a qualitative reading of the plots. The authors say "the primary focus of the discussion is the qualitative performance" (p.3).
- Varied: the operator request, and with it the parameters changed. Only nominal conditions were tested; there were no disturbances or mismatch (p.6). The choice among the four LLMs is not reported as an experiment, and no comparative results are given.

**Setup 2: LLM gives automated text analysis of performance (advisory).**
- Described (p.3), and it is claimed that gemma3:12b "was found to be capable of producing accurate explanations". No example output, accuracy measure or count is reported. There is no result on this feature.

## 5. Results
- Baseline (p.3): "Sensor T1 showed a 3.3◦ C overshoot with a 78 s rise time, while T2 showed a 2.3◦ C overshoot and a 96 s rise time." This is the reference for the other scenarios. Lower is better for both overshoot and rise time.
- Aggressiveness (p.4): CV.TAU for T1 went from 30 s to 5 s and for T2 from 30 s to 60 s. T1 "rose quickly to its new setpoint with a rise time of approximately 53 s (a 32% improvement over the baseline)". Overshoot stayed at about 3 °C, and T2 never overshot. The result is from a single run.
- Overshoot avoidance (p.4): tau went from 30 to 60 s for both temperatures, and there was no overshoot, "at the cost of a slower rise time which exceeded 400 s for both temperature trajectories". The LLM also issued redundant commands that left SPHI/SPLO at their default values (p.4). This is a qualitative sign of imprecise LLM output, but it is not counted.
- Smoothing (p.4–5): MV.DCOST on Heater 2 went from 0 to 10, then to 20 after a follow-up request. T2 "overshot the 40◦ C setpoint by less than 1◦ C, about a 1◦ C improvement from the baseline case". Heater smoothness is shown only in a plot.
- Limits (p.5): "All four commands were successfully transmitted and applied." Heater 1 stayed within 20–70%. T1 "briefly exceeded the upper limit" of 42 °C, because CV bounds are soft constraints. That reflects how the MPC treats CV bounds, not an LLM error.
- Overall claim (p.6): "closed-loop behavior consistently aligned with fundamental control trade-offs."
- **LLM vs non-LLM:** the paper does not show the LLM beating any non-LLM alternative. The improvements (32% faster T1 rise, about 1 °C less T2 overshoot) are against the untuned default MPC. They show that the requested parameter change had its expected effect, not that the LLM does better than a tuning engineer or an optimizer.
- Authors' stated limitation (p.6): "experiments were limited to a low-dimensional system (TCLab) under nominal conditions"; "robustness was not systematically evaluated against unmeasured disturbances or significant plant-model mismatch." They also note that output bounds are only soft (p.5).
- Timing: the LLM is said to respond "in real time" (p.3), but no latency figure is given. The MPC sample time is 5 s. The LLM is called on operator request, not at a fixed interval.

## 7. Terms to define
- TCLab: Temperature Control Lab, an Arduino-based board with two heaters and two temperature sensors used as a process-control benchmark.
- GEKKO: a Python suite for dynamic optimization and MPC (from APMonitor), with tunable attributes on manipulated variables (MV) and controlled variables (CV).
- CV.TAU: the time constant of the first-order reference trajectory that the CV follows toward the setpoint. Smaller values give faster, more aggressive control.
- CV.SPHI / CV.SPLO: the upper and lower edges of the setpoint dead-band. Deviations outside the band are penalized linearly (L1), making these soft output limits.
- MV.DCOST: the penalty weight on changes in the manipulated variable (move suppression).
- MV.UPPER / MV.LOWER: hard limits on the actuator value (heater %).
- MV.DMAX: the maximum change in the actuator per step.
- L1-norm objective: an objective that penalizes the absolute deviation outside the dead-band rather than the squared error.
- HITL (human-in-the-loop): every LLM-proposed JSON command needs operator "y"/"n" approval before it is applied.
- Insight generation / automated analysis feedback: an LLM-written text summary of controller performance from the logged process data.
- Pharma 4.0 / QbD: Industry 4.0 applied to pharmaceutical manufacturing; Quality by Design, a regulatory framework that requires critical process parameters to stay within bounds.
