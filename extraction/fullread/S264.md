# S264: Model Context Protocol for capabilities and skills in a lab manufacturing system

- Year: 2025.
- Title as printed: "Beyond Formal Semantics for Capabilities and Skills: Model Context Protocol in Manufacturing".
- Venue: arXiv 2506.11180v2 [cs.SE], 9 Dec 2025; self-described "work-in-progress paper" (p.1). No conference or journal venue is printed, so treated as a preprint.

## 2. Eligibility
Core. A general-purpose LLM (Claude Sonnet 4 in Claude Desktop) plans a multi-step job and calls machine skills through the Model Context Protocol (MCP). One skill triggers drilling on "a real production system via OPC UA" and another moves a Neobotix MMO-700 mobile robot through ROS 2 (p.3). The skills run their own state machines; the LLM picks which skill to run, in what order, and with what parameters (for example the spindle speed). That is an LLM connected to, and commanding, the skill/control layer of real equipment, tested in four scenarios (p.4). Domain: discrete manufacturing (drilling and transport), adjacent to process control. Evidence is lab hardware.

## 3. What was built, in plain words
The plant is a laboratory-scale manufacturing system with a drilling station and a mobile robot. It is real hardware (p.3). The controllers that move the actuators are the existing skill implementations, whose state machines "define the internal logic, state transitions, and safety behavior of a skill" and are unchanged by MCP (p.3). The LLM sits above them as an orchestrator.

MCP is an open protocol (from Anthropic) that lets an LLM client discover and call external functions ("tools") described in natural language (p.1). The authors expose three capabilities as MCP tools (p.3): (1) a "direct" MCP server, a Python script that looks up a recommended spindle speed (RPM) from material and drill diameter; (2) a "gateway" MCP server that wraps the drilling skill and calls it over OPC UA; (3) a ROS 2 capability that has the mobile robot pick up and move workpieces. Each tool's purpose, units and constraints are written as code comments. Constraints inside one capability (e.g. drill diameter limits) are coded as assertions that return structured errors; constraints between capabilities ("only after capability X") are text that the LLM must interpret (p.3).

The LLM receives the user's request plus the tool list and descriptions. It returns tool calls with arguments. Those calls go straight to the skills; the only check is each tool's own assertions. There is no human approval of each call, no simulation check and no separate verifier (p.3–4). Actuation is discrete: start a drilling operation with a given RPM, or a transport job. The model is not fine-tuned and uses no handcrafted prompt templates (p.2). Code and results are posted on GitHub (p.3).

## 4. Each tested setup
One setup: Claude Sonnet 4 orchestrating three MCP tools on the lab system (p.3–4). Four scenarios (p.4):
1. Standard job: drill a given workpiece (material, diameter), then transport it to assembly.
2. Unsupported drill diameter given by the user.
3. Workpiece starts at a different station, so a transport step is needed before drilling.
4. Material name not in the lookup table ("stainless steel" instead of "stainless").

Number of runs per scenario: NR (each is described once). Comparator: none; no non-LLM orchestrator, rule-based planner or explicit-model (ontology or Asset Administration Shell) baseline was run. Metrics: qualitative pass/fail on correct order and parameters. No timing, latency, or success rate across repeats. Varied: the task inputs and the initial workpiece location.

## 5. Results
- Scenario 1: "All skills were executed in correct order and with correct parameters." (p.4). The LLM computed RPM first, then drilled with that RPM, then sent the robot.
- Scenario 2: "The LLM correctly interprets the error response and reacts by prompting the user to select a supported drill diameter." (p.4). The assertion in the RPM tool caught the bad input; the LLM asked the human.
- Scenario 3: "The LLM infers the need for a transport step before drilling." (p.4).
- Scenario 4: "The LLM identifies "stainless" as a likely alternative and successfully retries the request" (p.4).
- Overall: "Across all scenarios, the LLM successfully planned and executed multi-step workflows" (p.4); that is 4 of 4 scenarios, apparently one run each. "No hard-coded control flow was required" (p.4).
- Authors' limitation: "our results are only an initial validation ... reliability and robustness – including hallucinations – remain an open challenge" (p.4).
- The paper does not show the LLM beating a non-LLM alternative; no comparison was made.

## 7. Terms to define
- Capability: an implementation-independent specification of a function with physical or virtual effect (p.1–2).
- Skill: the concrete, executable implementation of a capability, exposed through a skill interface (p.1, p.3).
- CSS: Capabilities, Skills and Services, a reference model for describing what manufacturing resources can do (p.1).
- MCP (Model Context Protocol): open client-server standard (JSON-RPC) for LLMs to discover and call external tools at runtime (p.1).
- Direct MCP server: tool that runs computation locally on the MCP host (p.2).
- Gateway MCP server: tool that wraps a call to an external resource over HTTP, OPC UA or ROS 2 (p.2).
- PropertyConstraint / TransitionConstraint: a constraint inside one capability (coded as an assertion) versus a constraint between capabilities (described in text for the LLM) (p.3).
- Asset Administration Shell (AAS): Industry 4.0 digital model of an asset; one of the explicit models MCP is proposed to replace (p.2).
- MES / SCADA: manufacturing execution system / supervisory control and data acquisition, here acting as MCP clients (p.2–3).
