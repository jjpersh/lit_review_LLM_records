## 2. Eligibility
Yes. A generative LLM (Claude Sonnet 4) sits in a "Monitor" agent and proposes corrective control actions (setpoint changes, SOP steps, operator notifications) with target SCADA tags and values. A deterministic validator checks these proposals before they reach an execution agent that would write to SCADA via OPC-UA. This is a process system: three fault scenarios derived from the Tennessee Eastman Process (TEP), a batch polymerisation reactor and a fluidised-bed dryer. All evaluation is offline on synthetic static scenario files. No SCADA writes and no plant or dynamic simulation take place. The paper still has tested setups of its own, so it is core.

## 3. What was built, in plain words
The AAE (Autonomous Action Execution) framework has four software layers that talk over MQTT, a publish/subscribe message bus. Layer A, the Monitor, is the only part that uses an LLM. It reads plant data and emits proposals in JSON. Each proposal gives an action type, a target tag, a value, a confidence score, a rationale, a priority P0–P3 and an optional SOP step. Layer B, the Orchestrator, merges and ranks proposals from several Monitors using a weighted confidence × anomaly vote. Layer C, the Verification Agent, is deterministic. It gives each action a PASS, WARN, APPROVAL or BLOCK verdict. Layer D, the Execution Agent, is the only component with SCADA write access. As designed, it would auto-execute PASS on P2/P3 actions, execute P1 only after operator acknowledgement, send WARN to an operator and never act on P0, which is left to the SIS (pp.4–6). In the evaluated prototype, the Verification Agent is cut down to six P&ID graph checks plus a scenario-specific "forbidden-action" regex rubric (p.5):
- tag existence
- actuatability (not a sensor)
- SCADA controllability (not a manual valve)
- loop relevance
- fail-state consistency
- downstream impact by breadth-first search

Before the LLM is called, pluggable analyzers condense the plant data into a structured text prompt (p.7):
- alarms
- trends, including detection of stuck values
- topology
- SOP steps
- broken loops

The plant data are hand-made JSON files: a P&ID, a SCADA snapshot, a 7-point time series at 10-minute intervals and an SOP (p.9). The LLM is prompted as a "process safety advisor" and must return a JSON schema. There is no fine-tuning. A VLM (Qwen2.5-VL-3B) is named for reading HMI screenshots, but it is not exercised in the reported results (p.10). Nothing is actuated: proposals stop at the validator verdict. The action types are setpoint changes, which would be continuous values.

## 4. Each tested setup
All setups use the same architecture: the LLM proposes and a deterministic validator gates. They are split by plant.

- **Setup 1: TEP fault scenarios.** The three scenarios are TEP_Reactor (cooling-water valve XMV_10 stuck at 42%), TEP_Separator (outlet valve XMV_7 stuck at 35%) and TEP_Stripper (controller windup with XMV_9 saturated at 92%) (p.8). These are static snapshots, not simulations.
- **Setup 2: PolyReactor**, a batch polymerisation reactor with cooling valve YC_Jacket_C stuck closed. The paper calls it the "best-case boundary".
- **Setup 3: Dryer**, a fluidised-bed dryer with heating valve YC_Heat stuck at 100% and only one actuatable valve. The paper calls it the "worst-case boundary" (p.8).

Experiments shared by all three setups (p.9):
- **Part A, context quality.** No LLM is used. Raw JSON is compared with the analyzer pipeline.
- **Part B, proposal quality.** One Claude Sonnet 4 call per condition (baseline raw JSON versus AAE prompt), scored against an author-made ground-truth rubric.
- **Graduated baselines.** Four prompt levels, B0 to B3, one run each.
- **Error injection.** 43 crafted proposals are fed to the validator: 35 unsafe and 8 valid. The validator is tested without the LLM.
- **Variance study.** 10 runs per scenario at temperature 0.7, 50 calls in total.

Comparators and metrics:
- **Comparators** are LLM against LLM: different prompt contexts. No non-LLM controller, rule-based diagnosis or optimizer is compared.
- **Metrics:** root-cause hit, tag validity %, hallucination %, SOP coverage %, required-action coverage %, safety compliance, P&ID pass score, confusion matrix and validator flag counts.
- **What was varied:** prompt context level, scenario and stochastic sampling. Only one LLM was used (p.17).

## 5. Results
- **Validator against injected bad proposals (all five scenarios):** "TP = 35 FP = 6 FN = 0 TN = 2" (p.12). TPR is 1.000 (35/35, higher is better). FPR is 0.750 (6/8, lower is better). Precision is 0.854 and F1 is 0.921. The author notes that the FPR rests on only 8 negatives (Wilson 95% interval about [0.41, 0.93], p.12). Per category: "hallucinated tags (100% FAIL), sensor writes (100% FAIL), physical contradictions (100% WARN/FAIL), forbidden actions (100% FAIL)" (p.12).
- **Variance study, TEP (Table 12, p.13):**
  - Violation runs (runs with at least one forbidden-action proposal, out of 10): 1/10 for each of the three TEP scenarios.
  - Hallucination: 0±0% on Reactor and Separator; "10 ± 11" on Stripper.
  - Validator flags: 10/10, 6/6 and 8/8.
  - Root cause: 1.0 in all runs.
- **Variance study, PolyReactor:** "0/10 (0%)" violation runs and 0% hallucination. All 10 flags are WARNs on valid proposals, so they are false positives (p.13).
- **Variance study, Dryer:** "7/10 (70%)" violation runs, hallucination "23 ± 3" (text: "22.5% mean"), flags 20/20 (p.13–14).
- **Aggregate over 50 runs:** 54 FAIL/WARN verdicts. "every actually unsafe proposal in the run set received at minimum a WARN verdict" (p.13). Caveat: this count mixes true positives with conservative WARNs, so it is a flag rate, not a catch rate (Table 12 caption).
- **Single-run baseline versus AAE (Table 9, p.11):**
  - TEP_Stripper baseline was unsafe (Safe = 0) and AAE was safe, but AAE "introduces tag hallucination (25% and 20%)" on Stripper and Dryer (p.11).
  - Dryer was unsafe in both conditions.
  - Root cause was hit in all 10 runs.
- **Graduated baselines (Table 11, p.12; mean of 5 scenarios):**
  - SOP% for B0/B1/B2/B3 is 100/90/35/75. Safety compliance is 0.6/0.6/1.0/0.8. P&ID score is 80.5/82.0/82.7/80.2.
  - "mean safety-compliance score drops from 1.0 (B2) to 0.8 (B3)" (p.12). The full pipeline is therefore not the safest prompt level.
- **Context enrichment:** the pipeline surfaces "on average 5.8 alarms, 7.4 trends, 1.4 broken control loops, and 6.0 SOP steps" per scenario, compared with zero pre-computed insights in raw JSON (p.14).
- **Latency:** aggregation takes "24.2 ms mean (σ = 3.1 ms)". LLM inference adds "approximately 2–8 seconds" (p.16).
- **No comparison with a non-LLM alternative.** The paper does not show the LLM beating a non-LLM method on anything. It mentions rule-based expert systems and PCA/SDG only qualitatively (p.16).

## 7. Terms to define
- **P&ID:** piping and instrumentation diagram. Here it is hand-transcribed into JSON and turned into a graph of equipment, instruments and valves.
- **SCADA:** supervisory control and data acquisition, the system the Execution Agent would write to via OPC-UA.
- **SOP:** standard operating procedure. Here it is a six-step troubleshooting guide for each scenario.
- **MQTT:** a lightweight publish/subscribe messaging protocol used between the agents.
- **Monitor / Orchestrator / Verification / Execution Agent:** the four AAE layers. In order, they propose, consolidate, gate and write.
- **P0–P3:** priority classes: imminent safety breach, active alarm correction, optimisation and informational.
- **PASS / WARN / APPROVAL / BLOCK (FAIL):** validator verdicts. Only FAIL/BLOCK prevents forwarding. WARN goes to an operator.
- **Forbidden-action rubric:** scenario-specific regex list of unsafe actions, such as "stop blower", taken from the author's ground-truth file.
- **Fail-state consistency:** a check that a proposal does not contradict a valve's fail-open or fail-closed behaviour under the diagnosed fault.
- **B0–B3:** prompt context levels, from a raw JSON dump to the full analyzer pipeline.
- **IPL / LOPA / SIS / SIL:** independent protection layer, layer of protection analysis, safety instrumented system, safety integrity level. The author does not claim that the AAE is an IPL or has a SIL rating.
- **TEP:** Tennessee Eastman Process benchmark (Downs & Vogel 1993).
