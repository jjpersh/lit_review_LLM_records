## 2. Eligibility
Eligible. An LLM agent uses tool calls to read and write variables on a Siemens S7-1500 programmable logic controller (PLC) over OPC UA. It is tested on a demonstrator PLC, scored on 50 commands with 5 models, and then demonstrated on an industrial spray-coating machine (a UR10e robot coating wire bundles). The LLM connects directly to the PLC layer and changes machine parameters and starts process sequences. The domain is discrete manufacturing and machine HMI rather than a chemical process, so it is adjacent. It is a tested setup, not a position paper, so it is core, but with weak control evidence.

## 3. What was built, in plain words
The paper replaces touch-panel HMI navigation with natural-language commands. The plant in the main test is a real Siemens S7-1500 PLC with four exposed variables: motorspeed (Float), temperature (Int16) and two text fields (String) (p.3). No physical process is attached as far as the paper states; the variables are simply PLC data points. A workstation runs an LLM client, an OPC UA client and an MCP server. MCP is the Model Context Protocol, a standard way to expose tools to an LLM; here it is built with Gradio (p.3). The LLM's system prompt holds a "nodes dictionary" (variable names, OPC UA NodeIds, data types) and a "machine credential list" (server endpoints and credentials) (p.2-3). The LLM receives the operator's text command and chooses among three Python tools: read, write (set an absolute value) and adjust (a relative change, absolute or percent). It then supplies the arguments. The tool does the arithmetic and writes the OPC UA node, so the LLM does not compute values itself (p.3). The tool result goes back to the LLM, which either calls another tool or replies to the user. Nothing sits between the LLM's tool call and the PLC write: there is no validator, range check or human approval. The authors only say these "can additionally be integrated" (p.4).

None of the models is fine-tuned; all are prompted only. They are GPT-5, GPT-5 mini and GPT-5 nano (snapshot 2025-08-07) through the API with MCP, and GPT-oss:20b and Qwen3:32B through Ollama with OpenAI-style function calling (p.3). The PLC writes are discrete parameter changes, not continuous control.

The spray-coating deployment (p.4-5) adds Whisper large-v3 for speech-to-text and Qwen3 TTS for speech output. The LLM is Qwen3VL-8B-Instruct, run with llama.cpp on one L40s GPU. It adjusts process parameters such as application speed and coating length, and it writes a string to an "action" variable. The PLC maps that string to a job number for the robot (for example "Apply Coating" or "Wipe Nozzle"). Each parameter has OPC UA min and max sub-variables that the LLM can read. The paper does not say whether these limits are enforced on writes.

## 4. Each tested setup
**Setup A: demonstrator PLC, 50 commands, 5 LLMs (p.3-4).**
- Commands: 50 synthetic commands generated with GPT-5 Chat and reviewed by the authors. Difficulty is set by how many parameters a command changes: 15 change one, 15 change two, 10 change three and 10 change all four.
- Run order: commands are sent in sequence, and all four parameter states are logged after each command.
- Scoring: a command is correct only if every affected parameter ends in the right state (all-or-nothing). Asking a clarifying question instead of acting counts as wrong. A follow-up command that executes correctly from a wrong starting state counts as correct.
- Runs: one run per model, with no repeats.
- What varied: only the LLM.
- Comparator: none. There is no touch-HMI or rule-based parser baseline.
- Metric: accuracy, meaning correct commands divided by 50, plus a classification of the errors.
- Reproducibility: the functions, the 50 commands and the logged responses are released on GitHub (p.6).

**Setup B: spray-coating machine deployment (p.4-5).**
- A qualitative demonstration with voice in and voice out, using Qwen3VL-8B.
- Figure 5 shows a sequence of commands: coat, clean the nozzle, then coat again with higher speed and length.
- No number of trials, no metric and no comparator are reported.

## 5. Results
- **Setup A, proprietary models (p.4):** "accuracy scores of 96.0 % for GPT-5 and GPT-5 nano, and 98.0 % for GPT-5 mini". That is 48 or 49 correct out of 50 commands. Accuracy is the share of commands whose final parameter states match ground truth, so higher is better.
- **Setup A, open-weight models (p.4):** "the open-weight models both achieved an accuracy of 90.0 %, or 45 out of 50 correct executions". This applies to GPT-oss:20b and Qwen3:32B.
- **Size made no difference among the GPT-5 models (p.4):** "the high-performance model GPT-5 does not outperform its smaller counterparts".
- **Error types (p.4, Table 2):** "Most of the errors (n = 9) were caused by incorrect execution of a tool, primarily due to omission of the minus operator". The categories are:
  - Sign errors: 9 errors over 5 models x 50 commands.
  - Repeated tool execution after misreading the tool result: 3, one by GPT-5 and two by Qwen3. In one case motorspeed was raised by 40 instead of 20.
  - Asking the user for confirmation: 1 (GPT-5 mini).
  - Misreading the verb: 2. For example, GPT-5 nano took "drop" to mean "set", so motorspeed was set to 5 instead of being reduced by 5.
  - Misusing a tool: 1 (GPT-oss:20b).
  - Several of these are unsafe-direction writes to a real PLC, such as increasing a value when told to reduce it.
- **Setup B:** only qualitative. Example output (p.5): "I increased the speed by 20% and started the process". No success rate is given.
- **LLM versus non-LLM:** the paper does not show the LLM beating any non-LLM alternative. No such baseline was tested.

## 7. Terms to define
- **OPC UA:** Open Platform Communications Unified Architecture, an industrial standard that lets a client read, write or monitor variables on a server running on a PLC.
- **NodeId:** the unique identifier of a variable in the OPC UA address space, e.g. "ns=4;i=12".
- **PLC:** programmable logic controller, the real-time industrial computer that reads sensors and drives actuators (IEC 61131-3).
- **MCP:** Model Context Protocol, an open protocol for giving an LLM access to external tools from a central server.
- **Function calling:** the LLM outputs a structured tool name and arguments that host code then executes.
- **NUI / HMI:** natural user interface (speech or gesture) versus human-machine interface, which today is typically a touch panel.
- **STT / TTS:** speech-to-text and text-to-speech modules wrapped around the LLM.
- **Adjust tool:** a tool that applies a relative change (a delta or a percent) to a node, so the LLM does not do arithmetic.
- **All-or-nothing criterion:** a command scores correct only if every parameter it affects ends in the right state.
