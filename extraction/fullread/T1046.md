## 2. Eligibility
Yes, this is a core paper. LLM agents propose setpoint changes for a simulated exothermic CSTR (continuous stirred-tank reactor), a process system. The paper tests a gated arm (proposals pass a shadow-plant simulator first) and a direct arm (proposals go straight to the plant) (p.5).

## 3. What was built, in plain words
- **Plant.** A simulated CSTR from OpsEnv, an open-source benchmark for LLM agents. It has mass, energy and level balance ODEs, an exothermic A → B reaction with Arrhenius kinetics, and 10 process variables (pp.4–6). Nothing runs on hardware.
- **Existing control.** A PI controller holds the vessel level by moving the outlet flow (p.4). The abstract calls it "proportional-integral cooling control" (p.1), so the text is inconsistent on this point.
- **What the LLM does.** At each step the agent gets the plant state and the scenario objective. It returns free-text reasoning with an embedded JSON proposal listing variable names, current values and new values, for example a coolant-flow change (pp.3, 5). These are discrete setpoint moves made once per step.
- **Prompting and models.** All four models get the same system prompt with units and safe ranges. There is no fine-tuning and no tool calling. "ReAct" here is a simplified single-turn variant (p.3, footnote). Temperature is 0 (p.6).
- **Parsing.** A regex extracts the JSON and a Pydantic schema checks it. If parsing fails, shadow agents hold the current setpoint and direct agents fall back to coolant flow at 1,500 kg/h (p.5).
- **PVC loop (Propose-Validate-Correct).** The shadow plant is a lightweight copy of the CSTR physics, integrated with SciPy LSODA (p.4). It works as follows:
  - It simulates each proposal N = 5 steps ahead (10 s each).
  - It checks variable bounds (e.g. T 413–523 K, Fc 200–3000 kg/h), rate-of-change limits, trip conditions and a stability rule (pp.3–4).
  - The stability rule: the proposal passes if the maximum normalized deviation from nominal is below 20%, or if it is no worse than the deviation before the proposal (p.4).
  - A rejected proposal returns feedback to the LLM, and the LLM may revise it up to K = 3 times before the case escalates to a human (p.4).
- **Orchestration.** LangGraph wires the loop and LangChain makes the LLM calls (p.4).
- **Direct arms.** These skip the shadow plant (p.5).

**How the shadow plant interacts with the agent, step by step (pp.3–5, 7–8):**
1. The agent receives the plant state, the objective, and the system prompt containing safe ranges.
2. The agent writes reasoning plus a JSON proposal. The parser extracts it. If parsing fails, the agent holds the setpoint.
3. The shadow plant checks the inputs against the range limits at the simulator boundary (p.12). It then simulates 5 steps forward and checks the trajectory for bound violations, trips and stability.
4. If the proposal passes, it goes to the "real" plant. In this study the real plant is also the OpsEnv simulation (p.5).
5. If it fails, the agent gets binary, descriptive or suggested-fix feedback (Table 1, p.5) and proposes again, up to K = 3 times.
6. If it still fails after K attempts, the proposal counts as rejected and the process state does not advance (p.7).

The paper does not report what escalation to a human means in the experiments (NR). It also does not say whether the shadow model differs from the "real" plant model (NR), so no shadow-versus-plant mismatch was tested.

**What a "shadow cell" is.** It is not a component of the plant. An "experiment cell" is one run of a given model × setup × scenario × seed × feedback level (p.6). "Shadow cells" are the cells whose setup includes the shadow plant (react_shadow or plan_exec_shadow): "all 222 shadow cells (Tiers 1–3; 282 including Tier 4)" (p.7; also p.15). The paper uses "per cell" and "per episode" interchangeably (pp.7, 10). So each shadow cell is one episode in which the shadow plant gated every proposal.

## 4. Each tested setup
- **Configurations (p.5).** There are four: react_shadow, plan_exec_shadow, react_direct and plan_exec_direct.
  - ReAct: the agent proposes one step at a time.
  - Plan-and-Execute: the agent drafts a multi-step plan, and each step is validated separately.
- **Agents' task (pp.5–6).** The agents ran 11 of OpsEnv's 21 scenarios:
  - A-series: setpoint changes that move the process to a new operating point.
  - B-series: disturbance response, where the agent must "diagnose and compensate for feed composition or flow disturbances".
- **How task completion was measured (p.6).** The completion score is the "normalized distance to the scenario objective", from 0 (no progress) to 1 (fully achieved). Higher is better, and success means 1.0.
- **Other metrics (p.6).**
  - Constraint exceedances that reach the real plant per episode (the primary safety metric; lower is better).
  - Wall time per episode.
  - PAR (Proposal Acceptance Rate) and SCSR (Self-Correction Success Rate) (p.8).
- **Experiment matrix: 440 cells in four tiers (p.6).**

| Tier | Cells | Models | Scenarios | Seeds | Episode length |
|---|---|---|---|---|---|
| 1 | 80 | Gemini 2.5 Flash | 5 | 2 | 15 steps |
| 2 (exploratory) | 72 | Qwen 2.5 32B, Llama 3.1 8B, Mistral 7B | 3 | 2 | 10 steps |
| 3 | 168 | Gemini 2.5 Flash | 7 harder | 3 | 50 steps |
| 4 | 120 | the three Ollama models | 5 harder | 2 | 50 steps |

- **Feedback levels.** Shadow setups were tested with three feedback levels. Direct setups used one (pp.6, 12).
- **Comparator.** The only comparison is the same LLM agent with and without the gate. There is no PID, MPC or optimizer baseline.
- **What was varied.** Gate on or off, architecture, LLM, feedback level and scenario.

## 5. Results
- **Safety with and without the gate (p.7, Table 2, Tiers 1–3).**
  - Gated setups: 0 violations. "Both shadow-equipped setups record zero violations in all 222 shadow cells."
  - Without the gate: "react_direct accumulates 10.4 mean violations per episode, while plan_exec_direct incurs only 0.2". This is a mean per episode over 49 cells each.
  - Interceptions: react_shadow 1,050, plan_exec_shadow 48 (Tiers 1–3). The intercepted proposals are concentrated in the upset scenarios B06 and B07.
- **Completion with and without the gate (p.9).** The gate costs little task performance, but equivalence is not shown.
  - "direct agents reach 0.584 mean completion and PVC-equipped agents reach 0.571".
  - "Cohen's d = −0.053, bootstrap 95% CI [−0.283, 0.174]". The TOST equivalence test gave p = 0.079, so equivalence is not confirmed.
  - Per setup (Table 2): react_shadow 0.575, plan_exec_shadow 0.566, react_direct 0.582, plan_exec_direct 0.587.
- **Per model (pp.7, 10, Table 3).**
  - react_direct violations per cell: Mistral 25.9, Llama 21.5, Qwen 11.8, Gemini 5.3. Mistral: "414 violations in 16 react_direct cells (25.9 per cell)".
  - Every model has 0 violations with the gate.
  - plan_exec_direct still produced violations: Gemini 8, Qwen 5, Llama 2, Mistral 2. Llama's and Mistral's were all in B07.
- **What the correction loop does (pp.4, 8–9).** It sends a rejected proposal back to the LLM with feedback, allowing up to K = 3 revisions.
  - Overall, over 11,335 proposals: "967 were accepted on first attempt (PAR = 0.085), 2,119 were accepted after correction". The aggregate SCSR is 20.4%.
  - SCSR is the share of proposals entering the loop that are corrected and accepted (higher is better). A-series: "SCSR = 40.3% (2,119 corrected out of 5,261 entering the loop)". B-series: 0%, because the 20% stability threshold re-rejects every revision.
  - PAR by setup: react_shadow 0.077, plan_exec_shadow 0.375.
  - The authors say the correction loop is what keeps completion near direct levels (p.9).
- **Rejections (p.8).** Of 8,249 rejected proposals, 1,552 would have caused real violations. The other 6,697 (81%) were rejected on stability grounds.
- **Feedback level (pp.11–12).** This uses the Gemini cells matched across levels in the A-series.
  - "descriptive feedback yields SCSR = 50.9% … a 3.0× improvement over binary feedback at SCSR = 16.7%".
  - Suggested-fix feedback: 53.6%.
- **Value of forward simulation (pp.12–13).** "For the scenarios evaluated, range checking alone sufficed to prevent all violations."
  - The 5-step forward simulation never caught anything that the range check missed.
  - Table 4 is analytical only: it shows that N ≥ 15 steps would catch a slow drift in B09.
  - A state-mapping defect in the shadow plant was found and fixed after the experiments (p.14).
- **Speed (p.10).** For Gemini, "60 s mean wall time compared to 1,835 s for react_shadow, a 31× reduction".
- **Beating a non-LLM method.** The paper does not show the LLM beating any non-LLM alternative, because none was tested.

None identified. OpsEnv is described as an existing open-source benchmark. The code is at github.com/mimran-khan/adipec2026 (p.6).

- 2026a: "From Detection to Action: Using LLM Agents for Fault-Tolerant Control"

The paper describes these as a "multi-agent framework integrating LLM agents with a Digital Process Plant Twin (DPPT) for fault-tolerant control, evaluated on CSTR and mixing-module benchmarks" (p.2). It treats them as having established the agent-validator-reprompt pattern without quantifying it across LLMs (p.3).

TCLab is not mentioned anywhere. The authors are a different group, and they use their own OpsEnv/PVC code rather than the Gill/Vyas digital twin or rig. This is independent work that cites the Vyas group as related work.

## 7. Terms to define
- **PVC (Propose-Validate-Correct):** the loop in which the agent proposes, the shadow plant validates, and the agent revises on feedback.
- **Shadow plant:** a lightweight CSTR simulator that forward-simulates each proposal for 5 steps before execution.
- **Shadow cell:** an experiment run (cell) in a setup that uses the shadow plant.
- **Experiment cell:** one model × setup × scenario × seed × feedback-level episode.
- **OpsEnv:** the open-source CSTR scenario suite (A-series setpoint changes, B-series disturbances).
- **Completion score:** the normalized progress toward the scenario objective, from 0 to 1.
- **PAR (Proposal Acceptance Rate):** the share of proposals accepted on the first attempt.
- **SCSR (Self-Correction Success Rate):** the share of proposals entering the correction loop that are corrected and then accepted.
- **K:** the maximum number of correction attempts (3).
- **N:** the shadow simulation horizon in steps (5).
- **Stability criterion:** a proposal passes if the maximum normalized deviation from nominal is below 20%, or if it does not worsen the existing deviation.
- **ReAct / Plan-and-Execute:** the step-by-step agent versus the agent that plans first and then executes.
- **Level 2.5:** the authors' placement of PVC in the Purdue model, between supervisory control and MOM (manufacturing operations management) (p.12).
