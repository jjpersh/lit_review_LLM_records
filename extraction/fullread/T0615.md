## 2. Eligibility
Core. A generative LLM (Phi-3 Mini, run locally through Ollama) turns a homeowner's natural-language query into a JSON tool call that launches and parameterises a model predictive controller (MPC) for battery scheduling, an appliance-time optimiser, rule-based baselines, or a direct appliance on/off command (p.6, p.10, p.20). Two tested parts: a 30-prompt tool-calling benchmark of four LLMs (p.10) and a simulated home energy system (p.13-18). Adjacent domain: home energy management (PV plus battery), simulation only.

## 3. What was built, in plain words
The plant is a simulated Indian household (Hyderabad): a 3.6 kW rooftop PV array modelled with pvlib from 2024 Solcast weather data, a 10.24 kWh Li-ion pack modelled electrochemically with PyBaMM/LiionPack (single particle model with electrolyte, SPMe), a Monte Carlo bottom-up appliance load at 15-min resolution, and real 15-min Indian Energy Exchange (IEX) prices (p.11-12). No hardware.

The controller that moves the actuator (battery charge/discharge power, continuous between -3 and +3 kW) is an economic MPC: 8 h horizon (32 steps), 15-min interval, cost objective of grid import minus discounted export plus a quadratic penalty on missing an 18:00 state-of-charge target of 7.2 kWh, solved with SciPy SLSQP in 1.82 s per step (p.8-10). An appliance tool searches time slots with the MPC to find the cheapest start time for a named appliance (p.15).

The LLM sits above all of this as an "orchestration layer". It receives the user's text and a fixed zero-shot system prompt listing nine tools (p.20) and returns a JSON object with `tool_name` and `parameters` (date, appliance). A Python router dispatches it directly; if a required parameter is missing, a regular-expression scan of the query fills it (p.13). There is no human approval, validator of tool choice, or simulation check before dispatch. The LLM then rephrases the tool's numerical output as a text answer (p.6, p.13). The LLM never sets battery power and does not change MPC weights or horizon in any reported run. The tool list includes `control_appliance` (direct on/off), but no run of it is reported.

## 4. Each tested setup
**Setup A: LLM tool-calling benchmark (p.10).** 30 hand-written prompts covering all tools (supplementary material). Four LLMs (Gemini 2.5 Flash via cloud; Llama 3 8B, Phi-3 Mini, Gemma 7B via Ollama) with the identical system prompt (p.20), against a keyword-matching parser. Metrics: tool-name accuracy, parameter-extraction F1, average latency. Single run per prompt as far as reported; no variance.

**Setup B: integrated LLM-MPC home energy simulation (p.13-18).** (i) One summer weekday, initial SoC 50%, comparing the reactive price-blind rule baseline, a heuristic price-aware rule baseline (charge below 25th price percentile, sell above 75th) and the MPC (Table 6, p.14). (ii) A dishwasher-shifting example: the MPC slot search picks a start time, compared with the "general MPC" day (p.15-16). (iii) Forecast horizons 3, 6, 8, 10 h versus the price-blind baseline, 7 days in each of summer, winter and monsoon, mean plus or minus SD across days (Table 7, p.16). (iv) SoC at 18:00 by season (Table 8, p.18). Comparators are non-LLM rule-based controllers; the heuristic one is the authors' own design, not tuned further. The LLM's role in these runs is only to invoke the tool; no run compares the LLM interface with a non-LLM way of calling the same MPC, and no LLM error rate in closed loop is reported.

## 5. Results
- Tool selection (p.10, Table 3): Phi-3 Mini "achieved the highest Parameter Extraction F1-Score (81.48%) while maintaining near-perfect tool-name accuracy (96.67%)", latency 0.703 s. Denominator 30 prompts (so 29/30 correct tool). Gemini 2.5 Flash: 100% tool accuracy but 37.29% parameter F1; Llama 3 8B 100%/72.41%; Gemma 7B 90.00%/72.41%; keyword baseline 70.00% tool accuracy and 77.78% F1. Higher is better. The keyword parser beats every LLM except Phi-3 on parameter F1, and Phi-3 beats it by 3.7 points.
- Single day (p.14, Table 6): net daily bill (negative means net income; lower is better) price-blind -15.23, heuristic price-aware -25.69, MPC -19.26 rupees. "the Heuristic Price-Aware Model adopts an aggressive trading stance, exploiting price fluctuations to maximize profit (| 25.69)" (p.16). So on cost the MPC loses to the heuristic rule baseline on this day, while winning on self-sufficiency (78.06% vs 40.17%).
- Dishwasher shift (p.15): "the Dish Washer's optimized schedule results in a net profit bill of | 21.05 ... compared to the general MPC's net profit bill of | 19.29". This is the abstract's "LLM-MPC versus general MPC" headline; the gain comes from the MPC slot search moving a 1.7 kW load to 21:15, not from the LLM. The 19.29 also disagrees slightly with Table 6's 19.26.
- Horizons (p.16-17, Table 7): monsoon "the baseline's mean daily bill is | 10.35, which drops to just | 2.70 for the 8-h horizon" (7 days; SDs about 12-19 rupees). Gains plateau beyond 8 h (summer 8 h -20.91 plus or minus 19.51 vs 10 h -21.13 plus or minus 19.41).
- SoC at 18:00 (p.18, Table 8): MPC 6.93-7.00 kWh against a 7.2 kWh target in all seasons; price-blind 2.05-8.10 kWh.
- MPC runtime 1.82 s per 15-min step; full-day simulation 175 s on a Colab T4 (p.13).
- The paper does not show the LLM beating a non-LLM alternative on a control metric. The control gains belong to the MPC, which beats the price-blind rule baseline on bill and loses to the heuristic price-aware baseline on bill in the one-day test. The only LLM versus non-LLM comparison is tool parsing against a keyword parser.

## 7. Terms to define
- HEMS: home energy management system that schedules PV, battery and appliance use.
- Tool calling: the LLM outputs a structured function name plus arguments that software executes.
- Zero-shot: a fixed instruction prompt with no worked examples.
- Parameter F1: harmonic mean of precision and recall of extracted arguments (dates, appliance names) against the curated answers.
- Self-consumption: share of PV energy used on site (load or battery charging).
- Self-sufficiency: share of household demand met by PV and battery.
- Net daily bill: import cost minus export revenue; negative means net income.
- SLSQP: sequential least-squares quadratic programming, a gradient-based nonlinear solver in SciPy.
- SPMe: single particle model with electrolyte, a reduced electrochemical battery model.
- IEX: Indian Energy Exchange, source of 15-min market prices.

## 9. Manuscript text

**4.1 Operator interface and explanation**
- Short version: In a simulated Indian home with PV and a 10.24 kWh battery, a locally run Phi-3 Mini turned homeowners' requests into JSON calls that launch an economic MPC or an appliance-timing tool, then explained the result in text. On 30 test prompts it chose the right tool 29 times (96.67%) with 81.48% parameter F1 in 0.70 s. <!-- p.10 -->
- Long version: Srinivasa Raghavan and Giridhar compared four LLMs as the language front end of a home energy manager on 30 hand-written prompts. Gemini 2.5 Flash and Llama 3 8B always picked the right tool but extracted arguments poorly (F1 37.29% and 72.41%). Phi-3 Mini picked the right tool 29 times in 30 and had the best argument F1 (81.48%). A keyword parser reached 70.00% tool accuracy but 77.78% F1, so it extracted arguments better than three of the four LLMs. <!-- p.10 --> Tool calls go straight to the controller; a regular-expression scan fills missing arguments, and nothing checks the tool choice. <!-- p.13 --> The study reports no error rate for the LLM inside the closed loop.

**4.3 Supervisory and advanced control (LLM-facilitated hybrid control)**
- Short version: The LLM only selects and parameterises the tool; an SLSQP-solved MPC with an 8 h horizon and 15-min interval sets battery power. Across 7 monsoon days, the MPC cut the mean daily bill from 10.35 to 2.70 rupees against a price-blind rule baseline. <!-- p.10 --> <!-- p.17 -->
- Long version: not needed.

**5.1 Head-to-head evidence**
- Short version: The headline gain (net income 21.05 vs 19.29 rupees per day) compares an MPC-shifted dishwasher with the unshifted MPC. It is not a test of LLM against non-LLM control. On the same single day, a heuristic price-aware rule controller earned more (25.69) than the MPC (19.26). <!-- p.14 --> <!-- p.15 -->
- Long version: This paper shows why integration studies need an arm that isolates the LLM. The abstract reports that "LLM-MPC" earned 21.05 rupees per day against 19.29 for "general MPC" and 15.24 for a price-blind baseline. The 21.05 comes from the MPC's own slot search moving a 1.7 kW dishwasher to 21:15. The LLM only passed the request to the tool. <!-- p.15 --> The paper's Table 6 shows a heuristic price-aware rule controller earning 25.69 rupees on that day, more than the MPC's 19.26, though with far lower self-sufficiency (40.17% vs 78.06%). <!-- p.14 --> No run compares the LLM interface with calling the same MPC directly, so the cost results speak to MPC, not to the LLM.

**5.2 Safeguards**
- Short version: The only safeguard is a regular-expression fallback that fills missing arguments. Tool choice is dispatched unchecked, including a direct appliance on/off tool, and no bad tool calls were injected. <!-- p.13 --> <!-- p.20 -->
- Long version: not needed.

**5.3 Timing**
- Short version: Phi-3 Mini answered in 0.70 s on average and the MPC solved in 1.82 s per 15-min step, so the LLM adds little time. The LLM is called per user query, not inside the control loop. <!-- p.10 --> <!-- p.13 -->
- Long version: not needed.

**5.4 Local and open-weight models**
- Short version: A 3.8B-parameter open-weight model (Phi-3 Mini on Ollama) beat cloud Gemini 2.5 Flash on argument extraction (81.48% vs 37.29% F1) and latency (0.70 vs 2.80 s) for home-energy tool calls, on 30 prompts. <!-- p.10 -->
- Long version: Here a small local model beat a cloud model and two larger local ones. On 30 home-energy prompts, Phi-3 Mini run through Ollama scored 96.67% tool accuracy, 81.48% argument F1 and 0.703 s latency. Gemini 2.5 Flash scored 100%, 37.29% and 2.801 s; Llama 3 8B 100%, 72.41% and 1.634 s; Gemma 7B 90.00%, 72.41% and 2.547 s. <!-- p.10 --> The authors argue that local deployment keeps household consumption data private. The test set is small: one prompt is worth 3.3 points of tool accuracy. Each prompt was run once, so no run-to-run spread is reported.
