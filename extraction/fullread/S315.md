## 2. Eligibility
Eligible. A generative LLM (Llama 3.1 8B) proposes control actions for a simulated microalgal bioreactor (Arthrospira platensis cultivation: pH, temperature, electrical conductivity (EC), growth rate). A middleware gate decides whether each proposal is executed (p.2–3). A bioreactor is a process system, so it is not adjacent. There is one tested setup, so the paper is core.

## 3. What was built, in plain words
The plant is a **simulation** of an A. platensis bioreactor with four sensors: pH (optimum 10.0 ± 0.05), temperature (32 °C ± 0.5), EC and growth rate (p.3). Each scenario covers 7 simulated days. The LLM is **Llama 3.1 8B, run locally through Ollama** (p.3). The paper does not report fine-tuning, prompt text or temperature. The code is on GitHub (p.3).

The LLM sits at the top of the loop. At each step it receives a JSON "context payload" that the gate builds. The payload holds the sensor readings, a trust score, the active autonomy mode and anomaly flags. The LLM answers with an `execute_action` tool call that names a discrete action category and gives a rationale (Table 1, p.2–3). Categories:
- ACT_UNRESTRICTED: "aggressive optimisation", meaning control parameters set to their optimal limits
- ACT_SAFE / HOLD
- passive actions: observe or notify
- request human verification

The paper never says what any category does physically to the plant model: no manipulated variable, setpoint value or actuator is described. Whether actuation is continuous or on/off is not reported (NR).

Before anything reaches the plant, the **Trust Gate** acts. It is built on the Model Context Protocol (MCP), a standard interface between an LLM and external tools. The gate has two parts:
- The **Trust Engine** computes a trust score from 0 to 1 using four detectors: a z-score outlier check, a cumulative-sum drift check, a growth-versus-temperature physics-consistency rule, and a stale-data/timestamp check. Each fault type subtracts a fixed penalty (p.2).
- The **Strict Policy** maps the score to an autonomy level: ≥0.8 full, 0.6–0.8 safe/HOLD only, 0.4–0.6 passive only, <0.4 human verification only.

A disallowed proposal is replaced by HOLD (p.2). The gate checks only the quality of the input data. It does not judge whether the LLM's decision is correct (p.2, p.4).

## 4. Each tested setup
**Setup 1: Llama 3.1 8B agent behind the Trust Gate on the simulated bioreactor, 8 scenarios (p.3–4).**
- Scenarios S1–S8 (Table 2, p.4):
  - S1: normal operation
  - S2: pH spike on day 3
  - S3: gradual pH drift
  - S4: missing EC data on days 3–4
  - S5: growth–temperature inconsistency
  - S6: pH timestamp anomaly
  - S7: prolonged pH drift
  - S8: combined drift and missing data
- Runs: one 7-day run per scenario, 56 decision steps in total (Table 3, p.4). Repeated runs are not reported.
- Comparator: none. There is no no-gate arm, no non-LLM controller (PID, MPC or rule-based) and no other LLM.
- Metrics: gate-behaviour counts (critical steps, aggressive and conservative proposals, overrides, "override accuracy", "unsafe execution rate"). No process metrics (pH tracking, biomass, constraint violations) are reported.
- What was varied: only the injected sensor-fault type.

**Action counts requested by the caller (all from p.3–4, Tables 2–3):**
- **Total proposals:** 56 decision steps in total (Table 3, p.4). Each step is one LLM proposal (p.2). Per scenario, 56/8 = 7 steps, matching the 7 days per scenario (p.3). The paper does not tabulate steps per scenario directly.
- **Overrides per scenario** (Table 2, p.4):

  | Scenario | Overrides |
  |---|---|
  | S1 | 0 |
  | S2 | 1 |
  | S3 | 0 |
  | S4 | 1 |
  | S5 | 0 |
  | S6 | 0 |
  | S7 | 5 |
  | S8 | 1 |
  | **Total** | **8** |

- **How many actions the gate allowed, restricted or blocked:**
  - 12 of 56 steps ran in a restricted autonomy mode (trust < 0.8) (p.3–4).
  - In those 12 steps the LLM proposed 4 conservative actions, which passed unchanged, and 8 aggressive actions. All 8 aggressive proposals were blocked and replaced by HOLD (p.3–4).
  - So 48 of 56 proposals were executed as proposed (44 at full autonomy plus 4 compliant in restricted mode) and 8 were overridden.
  - The paper does not count "restricted" separately from "blocked": every override is a replacement by HOLD.
  - Per scenario, the paper does not report the critical steps or the split of each scenario's proposals into aggressive and conservative. Only the overrides above are given.
  - The paper does not report how many ACT_UNRESTRICTED proposals were made in the 44 high-trust steps.

- **Did gating on input-data quality help compared with no gate?** The paper does **not** show this experimentally. There is no ungated run and no plant-outcome comparison. The only evidence is counterfactual. The LLM proposed aggressive actions in 8 of 12 critical steps, and the authors argue that "without an external trust-aware control layer, logically consistent yet unsafe actions may be proposed" (p.3). The 0% "unsafe execution rate" holds by construction. "Unsafe" means an action the policy forbids, and the gate enforces exactly that policy. The paper does not show what the 8 blocked actions would have done to pH, biomass or culture survival.

## 5. Results
- **Critical steps.** "Out of a total of 56 decision steps across all scenarios, 12 steps occurred under critical conditions" (p.3). That is 21.43% of 56 steps (Table 3, p.4).
- **LLM decision quality under bad data.** "the LLM proposed aggressive control actions in 8 cases" (p.3). Denominator: 12 critical steps (8/12). Table 3 gives 14.28% as a share of all 56 steps. The paper treats this as poor decision quality: the LLM does not take data reliability into account, even though trust flags were in its context (p.2–3).
- **Gate compliance.** "All 8 aggressive action proposals made under unreliable data conditions were successfully blocked … override accuracy of 100%" (p.3–4). Override accuracy is overrides divided by the aggressive proposals made in critical steps (8/8). Higher is better.
- **Override rate.** "The overall override rate of 14.29%, defined as the ratio of overridden actions to total decision steps" (p.4). 8/56; lower means less intervention.
- **Unsafe execution rate.** "The system exhibited a zero unsafe execution rate throughout the entire evaluation" (p.4). 0 of 56; lower is better. This is a policy-compliance metric, not a process-safety metric.
- **Scenario pass rate.** 100% (Table 3, p.4). "Pass" is not defined.
- **Internal inconsistencies:**
  - Table 3 lists "Scenario Pass Rate" with 56 in the Steps column.
  - The text says S8 trust reaches zero, "triggering complete blocking" (p.4), but Table 2 shows only 1 override for S8.
  - S5 (min trust 0.20) and S6 (min trust 0.00) show 0 overrides. This is consistent only if the LLM proposed compliant actions in those critical steps; the paper does not break this down.
- **LLM against a non-LLM alternative.** Not shown. There is no non-LLM controller and no no-gate baseline.

## 7. Terms to define
- **Model Context Protocol (MCP):** a standardised request–response interface between an LLM and external tools. Here it is extended with a gate (p.2).
- **Trust score:** a 0–1 rating of how reliable the sensor data are at a step. It starts at 1 and loses fixed penalties: timestamp anomaly −1, range violation −0.5, stale data −0.6, drift −0.2, inconsistency −0.3 (p.2).
- **Autonomy level / Strict Policy:** a monotonic mapping from trust score to the action categories the LLM may execute (p.2).
- **ACT_UNRESTRICTED:** "aggressive" actions that set control parameters to their optimal limits. Allowed only when trust ≥ 0.8 (p.2).
- **HOLD:** the safe default that replaces any disallowed action and keeps the system as it is (p.2).
- **Critical step:** a decision step with trust < 0.8 (p.3).
- **Override accuracy:** the share of aggressive proposals in critical steps that the gate blocked (p.4).
- **Unsafe execution rate:** the share of steps where an action the policy forbids was executed (p.4).
- **Stale data:** consecutive missing values that indicate a disconnected sensor (p.2).
