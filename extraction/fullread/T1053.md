## 2. Eligibility
Eligible as core, in an adjacent domain (motor drive). A general-purpose LLM agent (Claude) connects to a simulated IPMSM drive through an MCP server. It runs identification routines, sets the MTPA current reference, and changes the FCS-MPC cost weights and speed-PI gains of the conventional controller. The agent also proposes these changes to an engineer. There is one tested architecture. It was run as a single demonstration session and as two replicated single-shot studies (A1 and A2, N = 21 each).

## 3. What was built, in plain words
The plant is a **simulated** interior permanent-magnet synchronous motor (IPMSM). The model uses dq-frame equations, current-dependent saturation of the inductances and a mechanical load equation (p.3). The paper says a real DSP drive could replace it "transparently" (p.2), but no hardware was tested. The actuator is the inverter, which can only switch among a finite set of voltage vectors (on/off switching states, p.3). Those vectors are chosen by a conventional controller. That is either FCS-MPC (finite-control-set model predictive control, which each step picks the switching state that minimises a weighted cost of current error, switching and torque error) or an outer speed PI loop with bandwidth-tuned inner current loops (p.3).

The system has three layers (Fig. 1, p.2–3):
- **Plant layer:** the simulator, the controller and the identification routines.
- **Interface layer:** an MCP server (Model Context Protocol, an open standard for publishing tools to AI agents). It exposes 4 read-only resources and 17 tools in six groups (Table I, p.4).
- **Agent layer:** an unmodified Claude agent. It loads a CLAUDE.md instruction file at startup that defines its interaction mode, a commissioning checklist and domain formulas (p.4).

The agent receives resource reads, structured tool results and plots as inline images. It produces natural-language explanations for the engineer and tool calls such as `set_controller_weights`, `set_mtpa_reference` and `run_scenario`.

Every call goes through three checks before it can affect the plant:
1. per-tool argument validation in the MCP server, which rejects out-of-range calls with an error;
2. an engineer-approval gate that holds any state-changing call until the engineer consents;
3. plant-layer clamps that limit the current reference to i ≤ imax and restrict voltage vectors to the feasible set before every integration step (p.4–5).

The LLM is never in the real-time loop (p.4–5). There is no fine-tuning and no RAG (p.2).

### Where each safety limit sits (as requested)
- **Drive/plant layer, "Tier 1 hard physical constraints" (p.4):** current and voltage clamps, switching constraints and fault inhibits run at the controller sampling rate, independently of the agent. Concretely, FCS-MPC clamps the per-axis current reference to |i*| ≤ imax before each Euler step, and the voltage vector comes only from the inverter's feasible discrete set. The paper says a hard clamp on the *realised* current (cycle-by-cycle limiting or an overcurrent trip) would have to sit in the DSP firmware, outside the MCP scope (p.4). The realised iq did briefly reach about 12 A against imax = 10 A (p.5, Fig. 3).
- Fig. 1 and Section IV-A (p.2–3) place the current limit in the **interface layer** instead. They say current limits are "enforced here as soft rejects" and draw the i ≤ imax box in the MCP server. Section IV-E places the hard clamp in the plant. The paper is internally inconsistent on where the current limit lives.
- **MCP server, "Tier 2 soft engineering safeguards" (p.4–5):** (i) per-tool argument validation that rejects malformed or out-of-range calls; (ii) the engineer-approval gate for state-changing tools, while read-only tools and resources pass through ungated. The tool surface itself is also a limit: the agent has no code execution and only declared tools, so an adversarial chat message "can request nothing beyond the declared tool surface" (p.5).
- **Agent (CLAUDE.md, p.4):** a behavioural policy only. The agent works as a "guided co-pilot", pauses after each step and waits for confirmation before state-changing calls. An escape hatch lets the engineer opt into autonomous mode. Domain formulas are pinned to the server's sign conventions.

## 4. Each tested setup
There is one architecture (Claude + MCP server + CLAUDE.md + approval gate, on a simulated IPMSM with FCS-MPC/PI). It was tested three ways:
- **Demonstration session (p.5), one run.** The session covered these steps:
  - context acquisition;
  - resistance identification with a 5 V test;
  - a 5×5 flux-linkage sweep at 500 r/min;
  - MTPA reference at 7 A;
  - a 0.2 s baseline FCS-MPC scenario with λsw = 0;
  - a λsw tuning proposal;
  - a ramp load profile at 1000 r/min with speed-PI gain recommendations.

  There is no comparator. The engineer approval is visible in Fig. 3 ("Shall I proceed…" / "yes", p.6).
- **λsw sweep (p.5, Fig. 5 p.7).** The agent was asked to sweep λsw over four operating conditions: three load levels and one in field weakening. It produced a recommended λsw per condition, plus an unsolicited suggestion of gain scheduling. There is one run and no comparator.
- **Reproducibility studies (p.5–6).** Both start from the same baseline: λsw = 0, MTPA at 7 A, baseline scenario already executed.
  - **A1**, N = 21 single-shot trials: the agent is asked to investigate the d-axis ripple with no secondary objective given.
  - **A2**, N = 21 single-shot trials: the agent must meet fsw < 2000 Hz, which the baseline (about 2400 Hz) violates.

  The comparator for A2 is one **author hand-tune**: λsw = 1.00, ripple 0.90 A pp, fsw = 1800 Hz (Table II, p.6). This is a non-LLM expert baseline, but there is no optimiser or systematic search. Metrics are d-axis ripple (A peak-to-peak), mean switching frequency, constraint satisfaction, and choice of lever. The paper does not state whether the approval gate was active during the A1/A2 trials.

**The 21 trials (as requested).** "N = 21" is used for each of two separate studies, A1 and A2, each run 21 times from the identical baseline state (p.5–6). Per-trial values are said to be in the public repository (p.6).

**"Ambiguous objectives" (as requested).** The paper's wording is that the FCS-MPC cost (eq. 3) is "intrinsically multi-objective". So a request to "reduce the d-axis ripple" "admits several Pareto-feasible answers" (p.6): more switching penalty, asymmetric id/iq weights, a longer horizon, or accepting the ripple. A1 tested whether the agent would notice this or quietly pick one route. In all 21 trials the agent stated the ambiguity and asked the engineer for a secondary objective, with no silent commitments (p.6). In A2 the ambiguity was removed by a binding fsw constraint. The agent then picked the switching weight in 20/21 trials. The remaining ambiguity showed up as a wide spread in λsw (0.10–25.00), because the one-sided constraint lets any value below the ceiling pass (p.6).

## 5. Results
- **A1 ambiguity detection** (p.6): "Of N = 21 trials, the agent surfaced the ambiguity and asked the engineer for a secondary objective in all cases." 21/21 clarifying questions; higher is better.
- **A2 lever and constraint** (p.6): "A2 identified λsw as the correct lever in 20/21 trials, with all trials satisfying the constraint." The one off-lever trial chose the iq_error weight (Table II).
- **A2 dispersion** (Table II, p.6): "λsw median (IQR) 1.40 (0.70–2.00)", "range 0.10 – 25.00". 9 of the 20 switching-lever trials chose λsw = 2.0.
- **A2 performance vs hand-tune** (Table II, p.6): "final ripple_d median 0.85 A pp", "final fsw median 1643 Hz", versus the author hand-tune "ripple 0.90 A pp, fsw = 1800 Hz". Lower is better for both. The median LLM-chosen setting is slightly better than the single hand-tune on both metrics. This is the only LLM-versus-non-LLM comparison in the paper. It is against one manual setting and comes with no per-trial variance for ripple.
- **Demo baseline diagnosis** (p.5): "high d-axis current ripple (±1.5 A) … average switching frequency of 2675 Hz". These numbers describe the plant; the LLM was diagnosing them.
- **Demo load profile** (p.5–6): "speed overshoot of 200 r/min"; the realised iq overshot "to about 12 A" against imax = 10 A. The agent recommended "Kp = 2 A/(rad/s), Ki = 50 A/rad". There is no reported re-run with the softer gains.
- **Flux map interpretation** (Fig. 2, p.5): the agent flagged "Lq dropping from 12 mH to 8.11 mH at full current, a 32% reduction".
- **Sweep** (Fig. 5, p.7): the agent's recommendation table gives λsw 0.0–0.2 at light load, 0.5 at medium load, 0.5–1.0 at heavy load and 0.0 in field weakening, with gain scheduling suggested. These are agent output, not verified by the authors.
- **Latency:** not measured. The paper only states that LLM latency is "typically hundreds of milliseconds to seconds" (p.4).

## 7. Terms to define
- MCP (Model Context Protocol): an open standard by which a server declares tools and resources that any compatible AI agent can discover and call.
- Resource / tool (MCP): resources are read-only data; tools are callable functions that may change drive state or run simulations.
- CLAUDE.md: a plain-text instruction file loaded into the agent's context at session start, acting like a version-controlled system prompt.
- IPMSM: interior permanent-magnet synchronous motor, with saliency Lq > Ld that gives reluctance torque.
- FCS-MPC: finite-control-set MPC, which each step selects one of the inverter's discrete switching states to minimise a weighted cost.
- λsw: the FCS-MPC weight penalising switching transitions, which trades current ripple against switching frequency.
- MTPA: maximum torque per ampere, the d-axis current reference that maximises torque for a given current magnitude.
- Flux-linkage map: steady-state flux linkages recorded over an (id, iq) grid, showing saturation.
- Commissioning: bringing a new drive to its specified operating condition (identification, tuning, validation).
- Engineer-approval gate: a hold on state-changing tool calls until a human consents.
