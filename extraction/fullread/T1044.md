## 2. Eligibility
Core. A generative language model (Qwen 2.5 Coder, 7B and 3B parameters, run locally) writes the stage-cost function of a nonlinear MPC controller from a natural-language goal; the MPC then computes the control moves (p.4). This is tested in simulation on four systems, three tasks each, 100 runs per task (p.6). None of the four systems is a process plant: an inventory model, a five-reservoir water network, a marine uncrewed surface vehicle, and a crane trolley with a hanging payload (pp.6–7). All are adjacent domains; the reservoir network is the closest to process operation.

## 3. What was built, in plain words
Every plant is a simulated discrete-time model, s[t+1] = f(s[t], w[t]), with no hardware (pp.3, 10–11). The actuator is moved by a conventional nonlinear MPC: horizon N = 3, solved at each stage with SciPy `minimize`, applying only the first move (pp.3, 6). The LLM sits above the MPC and defines its objective. When a user types a new goal, a prompt is assembled from five fixed parts: a generic statement of the system form, an instruction to write a cost that "tends to 0 when the following goal is satisfied", hints to use squared target terms and min/max penalty terms for constraints, and an instruction to output only Python ending in `return c`. Added to these are a short plain-text description of the system and its state and control variables, the current state vector, and the goal text (pp.4–5). The model is not given the state equations. It returns Python code for `cost_function(s_t, w_t, t)`, which is extracted and plugged into the MPC (p.4).

There are two arms. In the "vanilla" arm the first valid cost function goes straight to the MPC. In the "self-assessment" arm (Algorithm 1, p.5) each candidate is first run through the nominal model over T stages. It is accepted only if (1) the average cost over the last M stages is at most c_thr and (2) the largest stage-to-stage cost increase is at most d_thr. Otherwise the LLM is queried again, up to k_max = 20 times (pp.5–6). Neither arm has a human approval step. The controls are continuous (thrusts, angles, releases, orders, force). The model is not fine-tuned. Sampling uses top_p 0.8, temperature 0.5, repetition penalty 1.1 and top_k 10, on an RTX 4090 PC (p.6).

## 4. Each tested setup
- Plants: inventory (3 items, 9-state, T = 20 stages); reservoirs (5 tanks, T = 50); USV SWAMP (6-state planar vessel with 8 inputs, T = 50–100); trolley (crane with payload, T = 500–1000) (pp.10–12). Three tasks per plant. The tasks include setpoints, ranges, coupled control constraints, holding the current state, obstacle avoidance and induced oscillation (pp.6–7).
- Arms: vanilla (one shot) versus self-assessment gate. These are separate setups because a gate checks the output.
- Models: Qwen 2.5 Coder 7B and 3B in the same architecture.
- Runs: 100 per task, per arm, per model (p.6).
- Metrics: N_end (valid code produced, in %); N_succ (true goal reached, judged by hand-made threshold conditions on the state and control trajectories, given in the Appendix); k_q (iterations the gate needed); t_gen and t_full (generation time, and generation plus one self-assessment simulation) (pp.6–8, 10).
- Comparator: none outside the LLM. There is no MPC with a hand-written cost and no other baseline. The only contrast is vanilla against self-assessment, and 7B against 3B.
- Off-nominal: none. The same nominal model is used for the gate and the simulation, with no disturbance, mismatch or fault (pp.3, 10).

## 5. Results
- 7B, vanilla: the paper reports that "in 9 cases (tasks) over 12 the 7B version of the LM is able to provide a success rate > 70%" (p.8). The mean N_succ is 77.17% over 12 tasks × 100 runs (Table 1, p.9). Per task it ranges from 32% (USV task 3, obstacle avoidance) and 49–51% (inventory tasks 1–2, with constraints) up to 98%.
- 7B, with self-assessment: "success rate N_succ now turns out to be at least 95% in 10 tasks over 12 and above 80% in all cases" (p.9). The table mean is 96.42% (text says 96.66%). N_end is 100% for all tasks. USV task 3 rises from 32% to 97%. The lowest task is reservoirs task 1 at 86%.
- Gate effort: "the average number of required iterations is 1.55 over all the tasks" (p.9; Table 1 says 1.59). The hardest tasks need about 2.3–3.2 iterations.
- 3B: "average success rate (Table 2) of 40.08% in the vanilla case and ... 56.25%" with self-assessment (p.9). Table 2 gives 40.25% and 56.5%. The gate raised performance "to a satisfactory level in only one task (inventory Task 1, from 30% to 88%)". On inventory task 3 it lowered success from 26% to 0%, which shows the gate rejects usable functions ("inherently conservative", footnote, p.9). On inventory task 2 it ended with valid code in only 80/100 runs. With the gate, 3B per-task success was 28–48% on the USV tasks (Table 2, p.9).
- Gate errors: the gate also accepted functions that missed the true goal. With the gate, success stayed below 100% even though N_end = 100% (for example 7B reservoirs task 1 at 86%, and 3B USV task 3 at 28%) (Tables 1–2, p.9).
- Timing: mean t_gen with 7B was 4.26–5.72 s, and t_full 6.17–9.89 s, depending on plant (Table 3, p.10). With 3B, t_gen was 3.38–4.57 s and t_full 4.89–7.80 s (Table 4). The authors say validated functions take "10–20 s on average" (p.10). They argue this fits task-level replanning, not fast loops (p.10).
- The paper does not show the LLM beating any non-LLM alternative. There is no hand-designed MPC cost or other baseline.

## 6. Duplicates
None known. The SWAMP vessel comes from the same group's earlier hardware paper (ref. [40]), but here it is only a simulation model.

## 7. Terms to define
- SLM (small language model): a language model with 7 billion parameters or fewer, run locally (p.2).
- Stage cost g: the per-step term summed over the MPC horizon. Here the LLM writes it as Python, and there is no terminal cost (p.3).
- Vanilla: one-shot use of the first valid LLM cost function, with no check.
- Self-assessment: a simulation gate on the nominal model that tests end-of-horizon average cost ≤ c_thr and maximum cost jump ≤ d_thr, and retries up to 20 times (p.5).
- N_end / N_succ: the percentage of 100 runs that produced valid code, and the percentage that met the hand-made goal conditions (pp.7–8).
- k_q: the number of LLM queries the gate needed in run q (p.7).
- SWAMP: a catamaran-shaped uncrewed surface vehicle with four azimuth water jets (p.6).

## 9. Manuscript text

**4.2 Design and tuning**
- Short version: Caccia et al. had a locally run 7B Qwen 2.5 Coder model write the MPC stage cost, as Python, from a plain-language goal on four simulated systems. The first valid cost met the goal in 77% of 1,200 runs. <!-- p.9 -->
- Long version: not needed.

**4.3 Supervisory and advanced control**
- Short version: Caccia et al. put a small LLM above a nonlinear MPC: each new user goal ("keep reservoir 3 at 5.5 and the others over 1.2") becomes a new MPC cost function. The MPC still computes every move. On an inventory model, a five-reservoir network, a surface vessel and a crane trolley, all simulated, the 7B model reached the goal in 96% of runs with a simulation check. Nothing was compared with a hand-written cost. <!-- p.4 --> <!-- p.9 -->
- Long version: not needed.

**5.2 Safeguards**
- Short version: Caccia et al. screened each LLM-written MPC cost by simulating it on the nominal model before use. For the 7B model this raised true goal success from 77% to 96% (12 tasks × 100 runs). For a 3B model it only raised success from 40% to 57%. <!-- p.9 -->
- Long version: Caccia et al. tested a safeguard against bad proposals that the model itself produced. Before an LLM-written MPC cost reached the plant, it was simulated on the nominal model. It was accepted only if the cost ended near zero and never jumped sharply, with up to 20 retries. <!-- p.5 --> Success was then judged by separate hand-made goal conditions. For Qwen 2.5 Coder 7B, success rose from 77% to 96% of 1,200 runs, and obstacle avoidance from 32% to 97%. <!-- p.9 --> The gate made errors both ways. It passed costs that missed the goal (86% success on one reservoir task with valid code in every run). With the 3B model it rejected every usable cost on one inventory task (26% to 0%). <!-- p.9 --> The check uses the same model as the simulated plant, so mismatch was never tested.

**5.3 Timing**
- Short version: On one RTX 4090 PC, the 7B model took 4.3–5.7 s on average to write a valid MPC cost, and 6.2–9.9 s including one simulation check. The authors put a full validated function at 10–20 s. That suits task-level goal changes, not loop-rate control. <!-- p.10 -->
- Long version: not needed.

**5.4 Local and open-weight models**
- Short version: Caccia et al. ran open-weight Qwen 2.5 Coder models locally to write MPC costs. The 7B model reached the goal in 96% of 1,200 simulated runs with a simulation check, while the 3B model reached 57%. <!-- p.9 -->
- Long version: Caccia et al. directly tested whether small open-weight models, run locally, can configure a controller. Qwen 2.5 Coder 7B and 3B ran on one consumer GPU and wrote the cost function of a nonlinear MPC from a plain-language goal. They were tested on four simulated systems, three tasks each, with 100 runs per task. <!-- p.6 --> With a simulation check and retries, the 7B model met the goal in 96% of runs, and in at least 80% on every task. The 3B model averaged 57%. The check brought it to a satisfactory level on only 1 of 12 tasks and made one task worse. <!-- p.9 --> Tasks with constraints were the hardest for both models. No non-LLM cost design or larger model was compared. So the study shows a size threshold, not an advantage over conventional design.
